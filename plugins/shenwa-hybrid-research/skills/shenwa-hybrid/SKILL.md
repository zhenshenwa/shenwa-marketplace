# 真深挖综合研究（True Shenwa Integrated Research）

把「AI 深度研究报告能力（深挖 Shenwa）」与「结构化金融数据能力（泛金融数据 Skill）」组合成一个**职责清晰、可校验、可个性化、可复制**的投研智能体模式。

一句话：**深挖出主体，数据源做校验；个性化全部外置；能力怎么调度不许动。**

## 何时使用

当用户要求：
- 做一份**单项**投研任务（公司深度研究 / 行业对比 / 事件复盘 / 每日复盘 / 标的筛选 / 趋势异动跟踪 / 量化因子分析），且希望**深度结论与可信数字兼得**；
- 按**客户个人偏好**（投资风格、时间视角、风险容忍、输出形态）定制报告；
- 需要一套**可复制给别人、别人还能自己改**的投研模式，而不是一次性报告。

> 只想要一份纯深挖报告 → 用 `shenwa` skill；只想查数字 → 直接用数据源 skill。本 skill 用于两者的**协同编排**。

## 一、四层架构（核心心智模型）

```
L1 · 偏好层  客户唯一可改区  →  profile.yaml（投资风格/时间视角/风险容忍/输出形态）
        │ 注入偏好参数
L2 · 路由层  【冻结】        →  任务受理 → 类型判定 → 分工定比 → 能力指派 → 交付形态
        │ 派发子任务
L3 · 能力层  【冻结】        →  深挖能力域（分析主体）+ 数据能力域（事实底座/校验层）
        │ 合并 + 校验
L4 · 输出层  由 L1 驱动变化  →  按偏好裁剪结构/深度/语言/格式/可视化
```

**分层原则**：L1 可改，L2/L3 冻结，L4 由 L1 驱动。客户改偏好只改变"输出长什么样"，不会破坏"能力怎么调度"。**偏好二分（v1.9.0）**：L1 分**表达偏好**（语言 / 长度 / 图表 / 结构 / 关注重点）与**任务约束**（期限 / 比较目标 / 风险限制 / 方法），**两类都只影响"怎么说"与"研究什么范围"，一律不得改写事实**。跨层修改（如新增数据源）属模式维护者职责，走版本升级。

## 二、50/50 分工的落地定义

| 维度 | 深挖（Shenwa） | 泛金融数据 Skill |
|---|---|---|
| **角色** | 分析主体供给方 | 事实底座 + 校验方 |
| **内容性质** | 定性、逻辑、深度结论 | 定量、时点、可核验事实 |
| **内容权重** | **约 50%** | **约 50%**（数据表 + 校验表计入） |

> 关键：**校验表是数据源的产出，必须计入那 50%**，否则会破坏 50/50。

### 配比浮动规则

| 任务类型 | 深挖 | 数据源 |
|---|---|---|
| 公司深度研究 / 行业分析 / 同业对比 | 50% | 50% |
| 事件复盘 / 政策解读 | 55%~60% | 40%~45% |
| 每日复盘 / 市场快报 | 30%~40% | 60%~70% |
| 标的筛选 / 选股 | 20%~30% | 70%~80% |
| 纯数据核查 | 0%~10% | 90%~100% |

**说明（v1.9.0 修订）**：上表是**建议区间**，不是硬性开关。实际比重与基准不同时，**只需在任务卡「分工声明」栏写明理由**；**不做自动回退**（旧版"未写明则自动回退 50/50"已作废）。比重调整**只影响分工呈现，不改变事实与证据状态**。

## 三、七步闭环 SOP（每次任务严格执行）

```
① 任务受理 → ② 偏好注入 → ③ 路由判定 → ④ 并行取数
                                          ↓
            ⑦ 归档修正 ← ⑥ 成稿交付 ← ⑤ 交叉校验
```

### ① 任务受理
补齐四要素——**标的、时间范围、交付物、交付格式**。缺失一次性问清，不问第二次。输出任务卡草稿。

### ② 偏好注入
读取 `profile.yaml`（若无，取 `presets/` 任一预设或按默认值），并把偏好分成**表达偏好**（语言 / 长度 / 图表 / 结构 / 关注重点）与**任务约束**（期限 / 比较目标 / 风险限制 / 方法）两组，生成生效参数集。客户临时指令（如"这次写保守点"）**本次覆盖但不改写偏好文件**。⚠️ **风格 / 风险容忍度 / 结论语气只改呈现，不改事实、数字与证据状态**；`data_weights` 是**阅读 / 关注权重**，不冒充已校准的量化模型（实现：`skills/shenwa-hybrid/scripts/preferences.py`）。

### ③ 路由判定
走决策树，**顺序不可颠倒**：

```
收到任务
  ├─ Q0 标的层级？【优先级最高，不可跳过】
  │    个股/单一主体 → 仅个股级能力
  │    板块/行业     → 板块级或行业级能力
  │    产业链        → 产业链级能力
  │    宏观/跨市场   → 宏观级或事件级能力
  ├─ Q0.9 数据形态？【v1.3.0 新增，优先级仅次于 Q0】
  │    【横截面】全市场/所有行业/哪些板块/排名/分布，或需横向比较 ≥3 个标的
  │              → 走「结构化直取」通道（S11 `get_right_side`），★禁止逐标的发报告
  │    【纵深】  单一标的（或 ≤2 个）深度解读 → 继续下面 Q1~Q6
  │    【混合】  既要名单又要解读 → 走「两段式」：先直取筛名单，再对 top-N 发报告
  ├─ Q1 只需事实/数字，不需判断？ → 是：【数据型】数据源主导（深挖 0~20%）
  ├─ Q2 核心是「市场数据加工」还是「逻辑判断」？
  │    数据加工为主 → 【数据型】数据源主导（深挖 20~30%）
  │    逻辑判断为主 ↓
  ├─ Q3 单主体还是多主体/行业？ → 【研究型】深挖 50% / 数据源 50%
  ├─ Q4 外部突发事件/政策驱动？ → 是：深挖 55~60%
  ├─ Q5 所选模板层级是否与 Q0 一致？
  │     个股  → 仅 {0,1,7,8,9,10,2001}；禁用 3002（板块级+重体量）
  │     板块  → 3002 / 3001
  │     行业  → 4 / 5 / 6
  │     产业链 → 3 / 11
  └─ Q6 模板择优复核【必做，不可跳过】
        把 tid=2001（智能深度推理）与 Q5 初选模板正面比较（v1.11.0 判据改版）：
          ├─ 唯一改选条件：本层级专项模板**覆盖不了用户已列出的问题**（覆盖缺口）**且层级为个股** → 改用 2001
          ├─ ⚠️ 指标族数量不构成理由：问题多 / 族多 ≠ 改选 2001；族少也不需要改选
          ├─ 其余情形保留初选（9=偏公司估值、3002=板块右侧监测 ……）
          └─ 无论选谁，都在任务卡「模板选型」栏写下比较结论与理由
```

### ④ 并行取数
深挖侧与数据源侧**并行**，不得串行等待：
- **深挖侧（v1.12.0 改版：发布一律经真实入口）**：`user_info` 查余额与有效期 → `templates` 匹配（**取模板 `cost` 作成本依据**）→ `publish_plan.build()` **生成发布计划**（`entry_id` **提交前生成**）→ `publish_plan.publish()` **逐份发布**（`gate()` 五项检查通过才真的调 `report_publish`）→ 取 aid **回填原条目**（**不按返回顺序分配报告**）
  - 🔴 **不得直接调 `report_publish`** —— 那样会绕开必要性 / 历史报告检查 / 计划覆盖 / 授权预算 / 参数一致性五项检查；**旧调用路径一律改经 `publish_plan.publish()`**
  - **（v1.13.0）背景与复用顺序**：**来源登记及核对**（材料 9 类追踪项，未知显式标记）→ **历史报告内容检查**（`reuse.judge_all()` **逐题**四档）→ **确定复用部分与研究缺口** → 对**必要的新报告**用 `publish_plan.assemble_background()` **组装背景**（核实数字带来源·时间·单位·口径；未核实标状态；用户观点写成待检验命题；**独立判断时不注入预设结论**；**不假设深挖能读本地路径 / 文件名 / 材料编号**；超限**不静默截断**，改调整条目 / 执行方式并**重新检查覆盖与预算**）→ 再走参数与发布检查 → 执行回填 → **证据处理**（复述检测 + 独立性自检）→ 逐题交付
  - `text`（背景消息）**必填**，短也要给；完全缺省会返回 `status=SRV` 参数缺失
  - 背景消息中的**日期必须与系统当日一致**，否则被深挖的**时间截面语义校验**拒绝
  - 每份报告按模板同步发起，但**发起即可返回**，不要阻塞等结果
- **发布前静态层级拦截（C10 修正）**：按 Q5 的「模板-层级静态映射」在**发布前**拦截，不依赖接口返回
  - 个股任务 → 禁止 tid=3002（板块级+重体量）、禁止 tid=12（市场/事件级）
  - ⚠️ **不要读发布回执的 `stocks`** —— 实测该字段在 `wfStartPublish` 回执中**恒为 null**（它是报告生成结果字段，只有完成后才在 `getDetail`/`getList` 中填充）
- **数据源侧**：并行拉取 D1~D8 所需数据
  - ⚠️ **财报相关数据（D2）一律优先从数据源取（v1.1 新增）**：三大报表科目、财报衍生指标、同比环比、财务比率，**取数入口只能是数据源**；深挖正文中出现的同类数字**仅作对照物**，不得作为取数来源，也不得因"深挖已给出"而跳过数据源取数
  - ⚠️ **每条数据按最小字段约定登记（v1.4.0）**：对象标识 / 指标定义 / 数值 / 单位 / 所属期间 / 公开或生效时间 / 取数时间 / 来源 / 处理方法；**缺失记「未知」，不补造**（实现：`skills/shenwa-hybrid/scripts/data_qc.py`）
  - **估值方法按「必要输入 + 适用条件」逐个判定（C15 修正 · v1.6.0）**：**不按用户风格强制方法**，也不再「必须有 D7 才能出估值」。D7（宏观与行业数据 + **板块估值分位**）是**相对估值类方法**（相对 PE / PB-ROE / PS）的**必要输入**，缺它只**停用该类方法**；绝对法（FCFF / FCFE 折现、股息率法）只要自己的输入齐备，即可在其**边界**内输出。齐备的方法**一个也算数**（不再要求「至少两种方法」）
- **必须向客户明示**：「一般 **1~5 分钟**，个别模板可能**超过 10 分钟**」，不得假装实时完成（实测耗时抖动达 10 倍以上：tid=9 为 52 秒，tid=1001 首测 >13 分钟）

### ⑤ 交叉校验（轮 0 → 轮 1 → 轮 2，顺序不可颠倒）
```
轮 0  数据口径统一 + 可比性检查 ← v1.4.0 新增，最先做：口径不一致就去比对 = 造伪偏差
轮 1  数据源内部一致性校验   ← 通过的数据才能作轮 2 基准
轮 2  深挖正文 vs 数据源      ← 后做（财报类数据以数据源为基准值）
```
> **轮 0 要做的四件事**：① 按最小字段约定登记（缺失记未知、不补造）；② 区分 半年度/全年/单季/TTM、
> MA/EMA、绝对/相对表现、指标水平/变化量、百分比/百分点；③ **先判可比性、再算差异**，
> 相对偏差的分母统一取**基准值**，基准为 0 / 近零 / 符号变化 / 不可比时**不机械套比例阈值**；
> ④ 跑**金额与单位检查 + 比例复算 + 摘要与表格一致性**（`data_qc.py`）。
> **数据冲突时保留原值与来源、标冲突，不擅自选一个数充当真值。**
> ⚠️ **财报类数字不参与"谁先谁后"的讨论，一律以数据源为基准值**：深挖正文中的财报数字只用于发现差异，不作为结论来源。
- 深挖 `report_status` 轮询至 public/private/error
  - **探测节奏**：前 2 分钟每 **10 秒**（短耗时模板最快 **52 秒**即可完成，30 秒轮询会白等），之后每 **30 秒**；上限 **40 次 / 20 分钟**
  - ⚠️ **轮询"调用异常" ≠ "报告失败"**：只有 `data.status == "error"` 才是报告失败；调用异常（超时/非 JSON/5xx）走重试+退避，连续 5 次则切换站点，仍失败只上报「无法获取状态」，**不得报"报告失败"**（曾因此把一份 52 秒即完成的报告误判为失败并空转 20 分钟）
- **动态层级复核（完成后兜底）**：读 `report_detail.stocks` 挂载数，个股任务 > 2 或板块/产业链 < 3 → 告警层级错配
- `report_detail` 读全文（**原文完整，不摘要**）
- **若含估值结论：先验「估值链输入锚点」（C13+C16）**：逐项核对 PE / PB / 股息率 / ROE / 增长率 / FCFF 基期；锚点失真只作废**真正依赖该锚点**的推演（不再「整链作废」），与该锚点无关的结论照常保留——**不因某个无关指标偏差而废弃整份报告**。⚠️ **不得因结论数字恰好落在合理区间而跳过锚点校验（C16）**——结论"碰巧接近"≠推导正确
- 抽取正文**全部**可验证数字，逐项与数据源比对，按**分层采信规则**判定
- 逐项检查是否存在**拦截级项**（偏差 > 50% / 量级错误 / 方向性误判）→ 发现即作废
- **多方法用于解释差异，不作为准入条件（C17 修正 · v1.6.0）**：**取消**「至少两种方法才算有效」——单方法在其边界内同样有效。方法齐备时并列呈现并**解释差异来源**（输入口径 / 假设 / 时点不同）；⚠️ **接近程度 ≠ 准确度**，**不得**因某方法结果偏低或偏离其他方法而剔除它，也**不得**静默取平均。另须先确认**现金流与折现率配对**：**FCFF↔WACC**（→ 企业价值，须再走权益调整桥）、**FCFE↔股权资本成本 Ke**（→ 股权价值，不再减有息债务）

> **必须先做轮 1 的原因**：实测曾在数据源内部发现 5 处矛盾（含 2 处 10 倍单位错误）。跳过轮 1 会拿错误数据去"校验"深挖，制造伪偏差。

### ⑥ 成稿交付
**先定交付形态**（短答 / 比较表 / 简析 / 完整报告，按任务深度与问题类型，**不按篇幅**），再按 `references/05-输出规范与校验表.md` 组装——**只有「完整报告」用六段结构**，其余形态按需要呈现，但**关键问题的回答必须完整、重要结论必须有依据、证据不足必须可见**。**格式转换不得改变结论 / 数字 / 验证状态**；深挖官方原文 PDF 标为「**原始报告**」，专家包综合版 PDF 当前环境**不支持生成**时须说明并改交 markdown / table / xlsx。
- 深挖分析主体照录（来自**归档件**），不摘要；归档件**完整保留全文**，含已确认错误的段落。**任何交付形态下归档都完整保留**；正文未附全文时**须给归档入口**（aid + 生成时间 + 来源 + 路径）
- **但全部数字以数据源为准**——深挖原文中的数字一律不得直接进入结论段与风险段
- **已确认错误的原文不得继续支持正文结论**；如需展示须标为「错误对照」，且不得进入结论摘要
- 事件类信息须已由数据源独立确认
- ★ **成稿前过「证据采信门」（v1.5.0）**：逐条把结论绑到其关键证据，按证据状态决定**保留 / 降低确定程度 / 改写 / 撤回 / 移入历史背景**；未独立核实的不进「已确认事实」；资料不足则收缩交付范围并说明缺项与影响。入口：`skills/shenwa-hybrid/scripts/evidence.py`

### ⑦ 归档修正
记录偏差与客户反馈；识别重复反馈模式；**同一类反馈连续出现 3 次 → 主动建议修改偏好并说明理由**。输出任务归档 + 修正日志。

## 四、模式红线（不可违反）

1. **数字分层采信**（最高优先级）——深挖数字可靠性是**分区的**：

   | 深挖输出的数字类型 | 采信规则 |
   |---|---|
   | **财报类数据**（三大报表科目、财报衍生指标、同比环比、财务比率） | ⚠️ **第一来源是数据源**：一律优先从数据源取数，深挖正文中的同类数字**仅作对照物**，不得作为取数来源 |
   | 推算类比率（比率/占比/增速/周转/覆盖倍数） | **不得引用**，一律以数据源计算值为准 |
   | 估值类数字（目标价/内在价值/DCF 值/估值倍数） | **不得引用**；深挖只可提供估值方法，数值由数据源代入 |
   | 阈值/价格类（买卖点/止损位/价格区间） | **不得引用**，由数据源技术面数据推导 |
   | 事件类信息（并购/订单/合作/监管动作） | 须由数据源独立确认后方可引用 |

   > 实测依据：45 项可核验数字整体一致率仅 33%，出现 3 处量级级错误；而主要引用已披露财报科目的那组一致率达 63%。**深挖的引用价值在于其分析框架、判断逻辑与推演路径，而非数字本身。** 财报数据作为最容易出量级错误、又最容易被下游直接引用的一类，**取数入口统一收归数据源**。

2. **不虚构**：任何数字必须来自数据源并标注来源与截取时点；无法获取就写"未获取"，不得估算替代。
3. **深挖原文完整归档**：不得摘要、改写、省略章节。但"完整归档"≠"采信其数字"，也≠"正文照抄"——**归档件完整保留全文（含已确认错误的段落）**，**正文只呈现认可的内容**；数字以数据源为准。**归档层与正文层作用对象不同，因此与红线 4「剔除」不冲突。**
4. **拦截级不得进入正文**：偏差 > 50%、量级错误、方向性误判的数字与结论一律作废；整段依赖它的**在正文中整段删除**。不得以"双值并列 + 标注存疑"变相保留。⚠️ **归档件照常保留该段落**（含编号 / 时间 / 来源），只是不得再支撑正文结论。
5. **事件须独立确认**：数据源无法确认的，作为"未确认事件"单列，**不参与情景推演与概率计算**。
6. **任务组织**（v1.9.0 修订，替代原「单一任务」）：**一个总任务允许包含多个子任务**（如「扫描 + 比较 + 解释」），子任务**共享经过验证的数据**、按键去重、同键不同值时**并列原值并标冲突**，最终形成**统一结论**；**不得**把与主题无关的事项打包。**互不相关**的多个任务拆成多张任务卡。**「仅查询」或「仅整理用户提供的材料」的请求不得自动扩展成新的深度研究。**
7. **口径一致**：同一任务内所有结论服从同一套偏好口径，不混用。
8. **可回滚**：偏好文件带版本号，每次变更留痕，可回退。
9. **合规底线**：不涉政治敏感、暴力非法、基于谣言的话题；产出为 AI 生成，重大决策前需人工复核。
10. **接入红线**（v1.1 新增，长期生效，优先级最高）：
    - **只走 API**：深挖一切能力经 API 端点调用，任何情况下不得用浏览器抓取或访问；
    - **无需邀请码**：登录**只需注册手机号（userID）**，**绝对不要向使用者索要邀请码**，也不得因缺邀请码阻断流程（接口层早已不校验；老凭据文件里若还留着 `inviteCode` 字段，忽略即可）；
    - **自动切站**：主站 `https://www.shenwa.top` 不可达时**自动切换备用站 `http://8.130.17.247:8088`**，无需人工确认；
    - 调用连续异常时在主备站之间重试退避，仍失败只上报「无法获取状态」，**不得谎报"报告失败"**。
11. **模板择优复核**（v1.1 新增，v1.11.0 判据改版，每次任务必做）：确定 tid 之前，仍须把 **tid=2001（智能深度推理）** 与初选模板正面比较一次（2001 是"按需求自适配分析流水线"的通用型**个股**模板，轻体量、2,297 字、5.5 分钟实测）。⚠️ **判据与指标族数量无关**：「任务跨多个分析维度」「需求描述偏模糊」「初选需多份拼凑」**都不是改选 2001 的理由**。**唯一合法的改选条件**＝**本层级专项模板覆盖不了用户已列出的问题**（覆盖缺口 `coverage_gap`）**且层级为个股**（`2001_eligible`）；层级不符时**不得**转 2001（板块 / 行业 / 产业链 / 宏观一律保留本层级模板）。无论最终选谁，都要在任务卡「模板选型」栏写明比较结论与理由，**不得跳过这一步**。实现：`scripts/router.py` 的 `template_for()`（`switch_reason.by_family_count = False`）。
12. **横截面任务不得逐标的发报告**（v1.3.0 新增，优先级仅次于红线 1）：「全市场 / 所有行业 / 所有概念 / 哪些板块 / 哪个行业 / 排名 / 分布」这类**多标的横截面**任务，**必须**走 Q0.9 的「结构化直取」通道（S11 `get_right_side`：一次调用覆盖全量精选池、**0 点、秒级**；实测为 62 个指数），**严禁**用 tid=3002 之类模板逐个板块发布——那是 `5 点 × N`，成本随标的数线性膨胀，而用户会误以为在做全量扫描。
    - 需要解读时走**两段式**：第 1 段 0 点直取筛出名单，第 2 段只对 top-N（默认 1~3）发报告。
    - 交付物**必须显式标注覆盖范围**——按**本次实际返回**填写（实测精选池为 62 个行业与主题指数，须注明口径来源；A 股概念板块有数百个，这 62 个是官方精选池），覆盖数量**不得写死**，**不得**写成"全市场所有概念"；四类名单**存在重叠，不得相加**。
    - 无 ADM/VIP2 权限时**如实告知**并说明可联系 `shenwa4119` 升级，**不得**偷偷退回逐标的发报告。
13. **结构化接口不免检**（v1.4.0 修正，取代原「等同行情数据、可直接使用、无需二次校验」）：`get_right_side` 的字段**不因"是接口原始输出"而豁免检查**。所见数据按**三层**分处理——**观测数据**（接口直给字段）/ **计算指标**（按明确公式算出）/ **模型判定**（深挖的状态、阶段、否决、迁移）；本地质量检查只管前两层，**模型判定不改判、不另造阶段标准**，字段业务含义（S0~S5）须引自 `skills/shenwa/SKILL.md` 的实测记录。必做的本地检查：**先按目标日期切截面**再统计；日期与代码唯一性、覆盖数量、重复记录、未知状态、**否决字段三态（True/False/缺失）**。⚠️ **缺失 ≠ 无否决**；**空结果 / 明确业务失败 ≠ 无异常**。实现见 `skills/shenwa-hybrid/scripts/right_side.py` 与 `data_qc.py`。
    - ⚠️ 与红线 1 的分工：红线 1 管「深挖**报告正文**里的叙述性数字」（不得采信）；本条管**结构化字段**的可核验性。**两者都不允许跳过校验**，只是手段不同。

14. **证据采信与结论确定程度**（v1.5.0 新增）：结论的确定程度**不得超过**其关键证据的状态（`verified` / `unverified` / `conflict` / `pending` / `missing`），**「有来源」≠「已独立核实」**。① 研究正文与原始资料分开：深挖原文**完整归档**（编号 / 时间 / 来源 + 含确认错误的段落），正文只呈现认可的事实、推断、假设与局限；② 已确认错误的原文**不得继续支持正文结论**，展示时须标「错误对照」且不进摘要；③ 关键证据失效 → 结论同步**撤回 / 改写 / 降级**；④ 允许明确标注的情景假设，**不得**用假设冒充已披露事实，用户观点先作**待检验命题**；⑤ 资料不足 → 交付能完成的部分 + 说明覆盖范围、缺项与影响，**不把有限样本写成共识**；⑥ 统计须有样本 / 分母 / 去重 / 时间口径，引用他方统计**保留归属**；⑦ **「已检查覆盖率」≠「已独立验证覆盖率」**；⑧ 证据充分时**保留明确结论**，不一律模糊化。实现：`skills/shenwa-hybrid/scripts/evidence.py`。

15. **表达与事实分离**（v1.9.0 新增）：**风格 / 风险容忍度 / 结论语气只改变"怎么说"**（顺序、措辞、语气、强调、版式），**不得改变**事实、关键数字、证据状态、结论判定与方法适用条件。**删除**「因为用户进取就增加上行情景概率或权重」这类规则。用户明确要求的不同假设情景**可以推演**，但必须标为**[假设变化]**（保留基准值），**不得**写成事实变化。实现：`skills/shenwa-hybrid/scripts/preferences.py`。

16. **交付形态按任务不按篇幅**（v1.9.0 新增）：交付形态分 **短答 / 比较表 / 简析 / 完整报告** 四种，由**任务深度与问题类型**决定，**不按内容篇幅**强制、**不做无理由自动回退**。**关键问题的回答必须完整、重要结论必须有依据、证据不足必须可见**。**六段结构只用于「完整报告」**，不强制用于所有任务；摘要式**正文可不附深挖全文**，但**归档件始终完整保留**并按需提供入口。**输出格式转换不得改变结论、数字与验证状态**；深挖官方原文 PDF 标为「**原始报告**」，**不得**冒充专家包综合报告；综合版 PDF 当前环境**不支持生成**时**说明并交付支持的格式**（markdown / table / xlsx）。

17. **权重语义与复合任务**（v1.9.0 新增）：`data_weights` 是**阅读 / 关注权重**（先看哪一类、取数勾选哪些、版式详略），**不是**已校准的量化模型，**不产生**加权评分；**不得**冒充已校准的量化模型。**复合任务**（一个总任务含多个子任务）应共享经过验证的数据、**按键去重**、同一键不同值时**并列原值并标冲突**，最终形成**统一结论**；**「仅查询」或「仅整理用户提供材料」的请求不得自动扩展成新的深度研究**。

18. **多维需求一条不丢**（v1.11.0 新增，优先级仅次于红线 1）：用户一次提出的**多个问题**必须**逐个登记、逐个回答**。⚠️ **问题数量 ≠ 指标族数量**：同一指标族可能含多个问题，一个问题也可能跨多个指标族 —— **不得因为在同一指标族内就把用户的不同问题合并掉**。路由 `step3_metrics()` 命中多族时**全部保留**（`families`），不再只取优先级最高的那一个；需求清单、取数、模板候选、校验、交付**每一环都要按问题逐项对齐**。统一问题清单见 `skills/shenwa-hybrid/scripts/requirement.py`。

19. **执行方式按证据缺口选，不按机械规则**（v1.11.0 新增）：**「出现分析二字」不触发报告**，**「命中两个以上指标族」也不触发报告**。判定顺序——① 已有接口能满足的事实查询 → **直接取数**（`direct_fetch`）；② 能由已有数据算出的量 → **直接计算并保留口径**（`compute`）；③ 现有资料足够支持的分析 → **用现有资料完成、不发新报告**（`existing_material`）；④ **存在实质性证据缺口、需进一步研究且模板能力匹配** → 才进入**报告候选**（`report_candidate`）；⑤ 有缺口但无匹配模板能力 → **如实列出缺口**（`blocked`）。一个任务**可组合**多种执行方式。⚠️ **不得把尚未实现的内容复用 / 预算功能写成已经具备**。交付前必须对照问题清单做**覆盖检查**（每个问题是否登记处理、有无静默遗漏）与**完成检查**（是否有足够证据并实际回答）；**存在未完成的必需问题时，整体不得标记为「全部完成」**。实现：`scripts/requirement.py`（`choose_execution` / `deliver_gate`）。

20. **报告发布一律经真实入口，不得绕过检查**（v1.12.0 新增，优先级仅次于红线 1）：每一次报告发布都必须有**明确的用途和任务条目对应**。发布计划由 `publish_plan.build()` 生成（每条含**提交前生成**的条目编号 `entry_id`），实际提交**一律经 `publish_plan.publish()`** —— 它先跑 `gate()`（① 必要性 ② 历史报告检查状态 ③ 计划是否完整覆盖用户要求 ④ 授权与预算 ⑤ 提交参数是否与计划一致），**只有 `decision == "proceed"` 才真的调 `report_publish`**，其余分支提前返回，**发布调用次数恒为 0**。🔴 **不得在 SOP 里直接调 `report_publish`**（旧调用路径同步改经该入口）。⚠️ **报告份数由模板能力、具体问题、有效复用共同决定**：**不得默认「一家公司等于一份报告」**，**不得为凑齐计划而给「直取 / 计算 / 已有资料足够」的问题新增报告**，**也不得把用户要求的对象静默缩减**。检查后若**对象 / 模板 / 输入材料 / 提交参数发生变化**，必须**针对变化重新检查**，不得沿用旧结果直接发布。

21. **预算三态与成本口径**（v1.12.0 新增）：预算必须区分**已结算消耗** / **尚未结算的预留占用** / **拟新增**；**已结算不再计入预留**。**账户余额 ≠ 用户允许本次全部花费的额度**（余额只作展示）；**数量提醒阈值不自动缩减研究范围，也不替代预算检查**。**预计成本 = Σ(各条目模板成本)**，来源 = `templates` 接口 `data[].templates[].cost`；**成本无法确认 → 标 `unknown`，绝不按 0 处理**，并**不得**在没有可核对成本时直接发布。模板价格只用于**估算**，**只有获得扣点依据才标「实际消耗」** —— 不得把模板估价直接写成已经扣点。并发执行时，**「检查剩余额度」与「预留本次成本」必须是一个不可被其他任务插入的操作**（`publish_plan.BudgetLedger.reserve()` 在同一把锁内完成），防止多个任务分别通过检查后合计超额。沿用既有授权规则：**已授权的范围与消耗内不再逐份询问**；超出授权时**只暂停受影响的未发布条目**，保留完整任务与待执行事项。

22. **提交状态、aid 绑定与结果未知的保护**（v1.12.0 新增）：条目编号**必须在提交前生成并保存**，**不得依靠返回顺序分配报告**；拿到 aid 后**绑定原条目**，再关联对象与问题；**并发乱序返回也不得串对象、串问题**。状态至少区分 `pending` / `submitting` / `accepted` / `done` / `failed` / `submit_unknown`（预算预留状态另记）。⚠️ **获得 aid 只代表服务端受理，不代表报告完成，更不代表用户问题已经回答** —— 不得据此把问题标为 `answered`。提交超时或连接中断**沿用既有 `submit_unknown` 保护**，**不自动换线路重新发布**；**结果未知时保留相应占用**，不因本地报错直接释放；**只有确认未产生消耗或得到明确结算依据后，才能调整占用** —— **服务端生成失败也不能直接等同于未扣点**。恢复任务时**先读取已有状态**，已受理或结果未知的条目**不得当作新任务再次提交**。复用检查只接通接口并记三态（`no_candidate` / `candidate_unverified` / `unknown`）；**内容有效性判定属第 4 轮**，本轮**不得宣称「五项检查全部完成」**，**也不得**把「查询失败」标成「已确认没有可复用报告」或当成生成新报告的理由（**内容有效性判定已由 v1.13.0 实现 → 见红线 25 与 `scripts/reuse.py`**）。

23. **背景要有据、可独立理解**（v1.13.0 新增）：发送给深挖的背景**一律经 `publish_plan.assemble_background()` 组装**，**并记录实际发送的文字**（`publish()` 回填 `sent_params` / `sent_text`，验收查这里）。**经核实且影响本次分析的数字可以传入**，但**保留来源 / 时间 / 单位 / 口径**；**未核实材料必须标明状态**；**用户观点表述为待检验命题**，**不得改写成已确认事实**；**独立判断当前状态时不注入预设结论**（`independent` 模式下 `existing_judgement` / `preset_conclusion` **一律不发送**）；**解释 / 验证已有判断**时可提供该判断并**注明来源 / 时间 / 用途**。**只选择本次研究需要的关键背景**，完整材料留在本地记录。🔴 **不假设深挖能读取本地路径 / 文件名 / 内部材料编号** —— 实际发送的文字必须**能独立理解**。压缩背景**不得改变**数字 / 单位 / 时间 / 条件 / 核实状态，**不得机械截断**。**超出 `text` 上限（500 字）→ 必须先调整问题条目或执行方式，并重新检查需求覆盖与预算**，**不得静默删除关键约束后继续发布**。

24. **来源关系：同源 / 复述不得充作独立证据**（v1.13.0 新增）：材料 / 来源记录至少能追踪 **对应对象与问题编号 / 材料编号 / 来源名称与可核对位置 / 材料所属时间·公开时间·获取时间（未知显式标记）/ 指标含义·单位·统计口径 / 核实状态 / 属于原始事实·计算结果·外部判断·用户待检验观点 / 与其他材料的引用·转述·底层同源关系**。🔴 **来源关系是补充信息，不能替代原有证据校验**（五态证据照旧）。**深挖复述已传入的背景数字，不算新增独立证据**；**不同接口引用同一底层材料，不自动算独立验证**；**来源关系无法确认时标 `unknown`** —— **不默认独立，也不武断认定同源**；**按具体证据判定**，**不因一处同源就把整份报告的其他证据全部归为同源**；**不得仅因两个结果一致就写成「两路独立验证一致」**。

25. **历史报告复用按内容判定**（v1.13.0 新增）：**报告列表 / 标题 / 模板编号 / 对象 / 日期只用于寻找候选**；**能否复用必须检查报告内容及其依据**（对象与层级 / 是否真正回答当前问题 / 研究截止时间是否适用 / 关键假设·情景·输入材料是否仍成立 / 报告是否完成且可读取 / 关键证据与校验状态是否满足当前用途），**逐题**给出四档之一：**完整复用**（作当前依据）/ **部分复用**（剩余缺口继续处理）/ **仅作历史参考**（不冒充当前结论）/ **不适用或待核实**（说明原因）。**不机械比对问题文字** —— 表述不同而问题相同、内容充分**可以复用**；**同日、同对象、同模板但研究问题不同不得直接复用**。**跨日内容不一律失效**：稳定结构性信息可用、**时效性数据须重新检查**；旧结论依赖**已变化数据**时**必须重新分析，不得只替换数字保留旧结论**。用户**明确要求新时点 / 新情景 / 重新开展研究**时，**不得用旧报告替换**。复用结果**关联问题编号**，完整复用的内容**进入该问题的证据与回答**（**不只是取消发布**）；调整计划后**重新计算预计新增消耗并核对已有授权**；**不得因后来决定复用而清除已提交 / 结果未知条目的状态与预算占用**；**不得为降低报告数量而降低研究深度或减少对象覆盖**。
实现：`scripts/reuse.py`。

26. **监测要留档、比较要在成稿前**（v1.14.0 新增）：**持续跟踪 / 与上次或指定日期比较 / 检验更新此前判断 / 已建立的监测序列**这四类请求进入监测流程（普通一次性查询沿用现有交付方式，**不强行增加无关趋势分析**）。**每次研究的事实与判断都要落成可追溯的监测记录**（记录编号 / 监测序列编号 / 任务与问题编号 / 稳定对象标识·名称·研究范围 / 研究截止时间·记录生成时间·材料时间 / 关键指标·数值·单位·统计期间·计算口径 / 证据引用·来源关系·核实状态·数据版本 / 当次判断·依据·假设·未确认事项 / 分析规则版本 / 数据缺口·样本范围 / 原始·修订·事后重建三分及其对应关系），**只记录实际获得的数据与判断，不为补齐字段编造内容**；**原始快照不覆盖**，数据修订 / 规则调整 / 判断修正**形成新记录并关联旧记录**；**同一任务重复归档不制造新观测**。**基线按「指定优先、否则取当前研究时点之前同序列最近的适用记录」选择**，**不按文件修改时间 / 下载顺序 / 返回顺序选**；**读取失败 ≠ 无历史**，不得覆盖已有记录。**比较前先查可比性**（对象 / 问题 / 指标定义 / 单位 / 统计期间 / 样本范围 / 分析规则），口径可统一则**重算另存**、不可统一则**标不可比及原因**、部分不可比**不妨碍其余继续**；**缺失值不补 0**、**基数 0 不硬算变化率**、类别按**状态迁移**比较；变化**区分数值差 / 百分比 / 百分点**。比较回答四问：**哪些变了 / 哪些有延续性 / 新证据支持·削弱·推翻原判断还是不足 / 变化来自对象本身·数据修订·口径·规则还是多因**（**允许「原因暂无法判定」**，不强行归因）；**数值上升 ≠ 改善、下降 ≠ 恶化**；**只有两个时点不得称持续趋势**；**事实变化与判断变化分开处理**，**规则变化或历史数据修订不写成研究对象变化**。**比较必须在成稿前完成**，最终回答呈现**本次结论 / 相比基线的主要变化 / 对原判断的支持或修正 / 待跟踪事项**，**没有变化可明确说明、没有依据不填充推演**；**保存失败如实说明，不宣称基线已建立成功**。需要新报告时继续经路由 / 内容复用 / 参数校验 / 发布检查 / 预算规则，**不得因新增监测就默认重生成报告**。实现：`scripts/monitor.py`。

## 七、校验判定表（轮 2）

### 校验顺序：先验「估值链输入锚点」，再验结论

深挖的估值结论是一条链：`当前 PE / PB / 股息率 / ROE / 增长率（输入锚点）` → `估值弹性表` → `DCF / 内在价值` → `目标价区间` → `折价与安全边际`。

```
第 1 步  核验输入锚点（PE / PB / 股息率 / ROE / 增长率 / FCFF 基期）
   ├─ 某锚点偏差 > 5%   → 只作废**真正依赖该锚点**的推演（不再「整链作废」），
   │                      与该锚点无关的推演照常保留
   └─ 锚点全部一致      → 再逐项校验估值结论
```

> 依据：某报告 3 个输入锚点全部失真（PE 18x vs 实际 15.98x、PB 3.2x vs 3.64、股息率 1.2% vs 2.80%），用"偏低的盈利基数 × 偏高的 PE 倍数"推出"折价 15%、安全边际充足"。**只作废依赖该锚点的推演（不再「整链作废」），既可避免对 6 个目标价与 4 个弹性系数的无谓逐项校验，又不牵连与该锚点无关的结论。**

### 内部一致性检查为**固定检查项**

每份深挖报告都要检查是否存在两处冲突表述（如"风险情景 -30%"与"悲观 -3.6%"并存）。发现即：标注报告缺陷 → 对该报告其余数字**降级采信** → 结论段不得沿用冲突结论。

### 判定表

| 偏差幅度 | 判定 | 处理方式 |
|---|---|---|
| ≤ 1%（或客户阈值） | 一致 | 采用数据源值，标注时点 |
| 1% ~ 5% | 轻微偏差 | 采用数据源值，脚注标注深挖原值 |
| 5% ~ 50% | 显著偏差 | 双值并列，标注「存疑」，提示人工复核 |
| **> 50%，或量级错误，或方向性误判** | **拦截级** | **作废，不得进入交付物；整段依赖它的整段删除** |
| 数据源无对应数据 | 无法验证 | 保留深挖值，标注「未经独立验证」 |

**两类特殊情形**：深挖**误报数据缺口**（声称缺失但数据源实际有）→ 以数据源为准补齐并**覆盖**缺口声明，不并列；深挖报告**内部自相矛盾** → 标注为报告缺陷，并触发对该报告其余数字的**降级采信**。

**口径冲突**（如深挖判断"景气上行"而资金流向持续净流出）：不做简单否定，**并列呈现 + 解释分歧来源**，写入「风险与情景」段。⚠️ **不得因客户偏好（`conclusion_bias` / `risk_tolerance`）而改判**——偏好只改**呈现顺序与措辞**（审慎 = 先列反面证据），**不改变**采信结论、证据状态与方法适用条件（v1.9.0）。

## 九、交付给客户的话术模板

> 本模式把「深度」与「可信」拆成两条线：深挖负责分析主体（逻辑、格局、推演），数据源负责事实与校验（行情、财务、资金、公告）。每份交付物都附一张**校验表**，逐项标注深挖数字与数据源数字是否一致——不一致到拦截级的，直接剔除不进入结论。
>
> 客户的个性化**全部外置在一个偏好文件里**，并分成**表达偏好**（语言 / 长度 / 图表 / 结构 / 关注重点）与**任务约束**（期限 / 比较目标 / 风险限制 / 方法）。改偏好**只改变"怎么说"与"研究什么范围"**，**不改变事实、关键数字与证据状态**——**同一套事实可以适配不同任务与表达需要**；交付形态按任务给（短答 / 比较表 / 简析 / 完整报告），简单任务简洁交付、复杂任务保留必要证据。文件带版本号，可随时回滚。

## 十、深挖接口升级检测（手动 SOP）

> ⚠️ **v1.2.1 变更：已移除 `hooks/`**。本包原先内置会话启动钩子自动探测版本，但**官方校验器明确把 `hooks/` 列为专家包禁止目录**（`validate_expert.py`：`Forbidden directory found: hooks/`），且官方打包脚本 `package_expert.py` 会**先校验、不通过即中止打包**。为让包结构与官方规范一致、避免接收方导入时被安全检测拒绝，**钩子已彻底移除**，版本检测改为下面的手动 SOP。

### 手动检查（会话首次响应前，一条命令）

```bash
# 查官方最新版本（主站失败会自动切备用站），返回 data.latestVersion
$PY <本包>/skills/shenwa/shenwa_api.py latest_version

# 看本地已跟踪的版本
ls <本包>/skills/shenwa/shenwa_config_*.json
```

- 官方版本**更高** → 主动、简短地告知用户，并询问是否现在升级；用户说稍后处理则同一版本不再重复提醒。
- 版本**相同** → 静默继续，不必打扰用户。
- 工作区若残留旧的 `深挖版本跟踪/版本检查报告.md`，**该文件可能已过期，一律以本次实测为准**。

### ⚠️ 只报告，不自动覆盖（这是刻意设计，不是未完成）

自动覆盖官方最新配置会**抹掉本地补丁**，其中最关键的一条至今仍必须保留：

> 🔴 官方（截至 1.0.6）仍把 `inviteCode`（邀请码）标为必填，且 `login.inviteCode.required=true`。一旦用官方配置覆盖 `shenwa_config_*.json`，**「反复索要邀请码」的问题立刻复发**，而新用户根本没有邀请码。

此外还会抹掉作者本机路径脱敏、`shenwa_api.py` 接口注册表扩展等本地修正。

### 升级怎么做（必须人工确认后执行）

1. `GET /api/manage/getLatestVersion` 拿 `latestVersion` 与 `configFilePath`，下载新版配置。
2. **先修 JSON 语法**：官方 schema 里有未加引号的占位符（如 `"date": <日期>`），`json.load` / `JSON.parse` 会失败，先补引号。
3. **补丁式合并，不要整份覆盖**：保留 `_local_patch`（删除 `auth.user_credentials` 的 `inviteCode` 项、`login.inviteCode.required=false`）。
4. ⚠️ **路径与响应结构一律以实测为准，不要照抄官方配置**：官方 1.0.5 曾把 `get_right_side` 的路径写成 `/api/api/market/getRightSide`（双 `api`），两站实测均 **404**；真实路径是 **`/api/market/getRightSide`**（实测 HTTP 200）。**官方 1.0.6 已修正该笔误**，本机配置已同步。其响应 schema 被写成 `data[].values[]` 嵌套，实测是**扁平结构** `data[]` 直接含 `date`/`code`/`name`/`data`。
5. 同步 **全部 3 份副本**：`~/.workbuddy/skills/shenwa/`、`shenwa-agent/skills/shenwa/`、`shenwa-hybrid-research/skills/shenwa/`；两个专家包升版重打包。
6. 升级后**必跑「本地补丁自查」**（见 `shenwa` skill 文末），确认邀请码问题未复发。

> 判断字段是否真需要、路径是否写对，**唯一可信依据是实测接口**，不是官方配置文件、也不是文档。
